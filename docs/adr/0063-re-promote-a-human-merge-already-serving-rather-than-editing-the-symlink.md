# Re-promote a Human Merge already serving rather than editing the symlink

Post-Promotion Production Appearance Verification (ADR-0062) only runs inside a Promotion that switches. It has to: "card view is unchanged" is measured against the Release production served *before* the switch, and comparing a Release to itself proves nothing. `promote-keeplore-main.sh` is idempotent by design — a commit already serving exits with `Keeplore already serves Release <commit>` and switches nothing — which is what makes a duplicate webhook delivery and a reconciliation pass safe.

Those two facts together leave a merge that reached production before appearance verification existed permanently unverifiable. The Keeplore Button Trial's own merge is exactly that: `JacobStephens2/keeplore#4` was merged at 2026-08-25T11:53Z and `4cc29d1d` promoted a minute later, months of trial rounds before the verifier was written. Re-running the promoter against it captures no baseline and produces no verdict, so five of issue #14's acceptance criteria cannot be ticked against it.

The workaround an operator reaches for is switching the `current` symlink back by hand so the promoter runs again. That is the unrecorded production mutation the whole design refuses: it leaves no Promotion Attempt, no Evidence Record, and no rollback target, and it means the state production was in for those minutes exists only in the operator's memory.

`repromote-keeplore-merge.sh` is the supported alternative. It steps production back to the Release the merge replaced, promotes the merge commit again through `promote-keeplore-main.sh`, and records both moves as Promotion Attempts. Every switch it makes goes through the promoter that already knows how to preflight, switch atomically, verify, and roll back. It never touches the symlink itself.

Re-promotion is a separately named operation rather than a flag on Promotion. Ordinary Promotion stays idempotent, so a duplicate webhook and a reconciliation pass still return the recorded result and deploy nothing; only an attended operator running this program re-verifies anything. Nothing in the Voice Agent, the webhook path, or the reconciliation timer can reach it.

It refuses unless all of it holds before anything moves: the active Deployment Contract revision verifies appearance, the named commit is a verified Human Merge, that commit is what production is serving right now, the journal records which Release its Promotion replaced, and that retained Release is still on disk as an immutable Release. Discovering any of these after the step back would strand production on the retained Release for a merge that was never eligible.

Which Release to step back to is read from the append-only Promotion Attempt journal, not guessed from the Release root. The newest other Release on disk is not necessarily the one the merge replaced, and a step back to the wrong one would measure the merge against a baseline nobody promised. A re-promotion's own step back and restore are excluded from that lookup, because the step back's `previous` is the merge commit itself — reading it back would step the next re-promotion onto the Release it is verifying, which is the comparison-against-itself the operation exists to avoid.

Each attempt the re-promotion makes carries `repromotion: { kind, mergeCommit }` in the journal. `step-back` and `restore` are health-verified only; holding a Release that was already promoted to the merge's own acceptance bar would measure the wrong Release and roll production somewhere nobody asked for. `candidate` is the attempt verified in full, and it is the one that carries the appearance verdict.

The window during which production serves the retained Release is stated to the operator before the run starts, and a third of it is reserved up front for the restore that ends a failed run — a bound that only covered the happy path would not be one. `KEEPLORE_REPROMOTION_WINDOW_SECONDS` declares it, between three minutes and an hour, and defaults to fifteen. Only a re-promotion reads it and only a re-promotion refuses over it; a window nobody is using is no reason to fail every Promotion and health check on the host.

It is enforced as a deadline the Promotion must switch before, not as a signal that could cut one in half. The promoter reads `KEEPLORE_SWITCH_DEADLINE` once, immediately before the switch and after the phases that run while the retained Release is still serving — the preflight and the appearance baseline — and a passed deadline is recorded as an attempt that changed nothing. Past the switch the Promotion runs to completion: one killed between switching and recording its attempt would leave production somewhere the journal does not know about, which is worse than overrunning.

## Consequences

No successful run ends with production on the retained Release, and a failed one does not walk away from it either. A candidate Promotion that fails restores the retained Release, as any Promotion does; the re-promotion then restores the merge commit through the promoter — another recorded, health-verified Promotion Attempt — so production returns to the Release it was serving before the operator started. That restore is attempted whenever production is not on the merge commit rather than only when it is on the retained Release, because the promoter's rollback has more than one landing place. If the restore itself fails, the promoter has restored the Release it found serving; it is healthy, it is named, and the merge stays unverified. Every exit that is not a completed re-verification names the Release production is on and whether it is answering.

A merge whose retained Release has already been pruned cannot be re-promoted. `KEEPLORE_RETAINED_RELEASES` decides how long that stays possible, and the honest answer once it is gone is to verify the next Human Merge instead.

The trial's Evidence Record projects a re-promotion as verification of the original Human Merge rather than as a second merge. The merge event is taken from the original Promotion, so it keeps the actor and the time the human actually merged; the step back and the restore appear in the history as their own events and decide nothing about the conclusion. A `restore` succeeds at the promotion stage and must never read as the merge having been verified, which is why the projection derives promotion, rollback, health, and Release from the candidate attempts alone.

`KEEPLORE_MERGE_SOURCE=attended` is a third merge source alongside `webhook` and `reconciliation`. It describes how this attempt reached the promoter, not how the merge happened; the merge is still the original Human Merge, and a journal that holds the original Promotion still projects `webhook`.

The Keeplore tools now resolve the Human Merge verifier beside themselves, falling back to the release orchestrator's directory, the same way the GitHub App credential helpers already did. The attended deployment-authority upgrade installs `verify-human-merge.sh` with them, so a re-promotion can refuse an unverified commit before it moves production.

Re-promotion is worth reaching for only when slice three needs closing against a merge already serving. The alternative — activate appearance verification and let the next real Keeplore Human Merge prove it end to end — needs no new code, moves production once instead of twice, and remains the recommended path.
