# Raise a detection-time recognition failure at the recognition stage

A failure of the recognition provider during machine detection was never attributed to OpenAI, as ADR-0057 and issue #131 both recorded. It was never attributed to anyone. The detector was handed its transcriber as a model name, so the framework built and ran it inside a private pump whose faults reach nobody: a gateway error is emitted on the transcriber and, with no listener for it, swallowed where that pump is started. Detection then reached its no-speech timeout and returned `uncertain`, which this system fails as `machine-not-human` and answers with voicemail. A recognition outage therefore hung up on every caller who answered, recorded no provider failure, wrote no operator line, and moved no counter — a silence worse than the misattribution it was mistaken for, because it points diagnosis at nothing at all rather than at the wrong vendor.

The detector is now given a transcriber this system constructs, under the same bounded connect options as the conversation transcriber, and a fatal error it reports raises a bounded failure of the recognition provider. That failure is recorded at the existing `stt` stage rather than a new one. Detection is the recognition provider doing recognition work, and its fault is diagnosed by moving off the gateway exactly as a recognition fault during a turn is; a `detection` stage would split one provider's outage across two series and add a contract member, a retry classification, and a rollup label to say something the `stt` series already says. The cost is that `stage=stt` no longer means "during a live turn": the series gains faults raised before the call was answered, which is a discontinuity in what it counts rather than a change to any record already written.

The wrap that produced the `coordinator` attribution is corrected with it. What actually escapes the detector is its classifier's own call — genuinely the interpretation provider's, and left at `coordinator` — and its lifecycle: a detector closed underneath a run, a run started twice. Those are this system's faults and now report at `agent`, which is what ADR-0052 established that stage for and the one attribution issue #131 correctly identified.

## Consequences

The Bounded Provider Retry classification is unchanged. A detection-time fault is raised on the path that ends the call before it is authenticated, so it is terminal under ADR-0044's fail-closed ending and reaches the prerecorded response and the end of the call exactly as before; ADR-0049's single retry belongs to the finalized turn pipeline and never saw this stage. What the classification gains is a timeout: a recognition fault carrying the provider's own `APITimeoutError` is now recorded as `provider-timeout` against the recognition timeout rather than as nothing.

The operational rollup counts these under `stage=stt` with the recognition provider's identity, so `voice_agent_telephone_provider_failures_total{stage="stt"}` and the boundary failure counter both step on a detection-time outage. An operator reading a run of `stt` failures can no longer assume every one of them happened mid-conversation, and the Evidence Record still carries no description of the fault.

Owning the transcriber moves two responsibilities to this repository. The framework no longer closes it, so the detector's own close does; and it now runs under this system's bounded retry and timeout rather than the framework's defaults, which is what makes a dead gateway fail promptly instead of burning the detection window in silence. A gateway that fails without reporting an error frame still degrades the old way — to `uncertain`, and to voicemail — because there is nothing for a listener to hear.
