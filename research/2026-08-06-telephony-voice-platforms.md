# Telephone and realtime voice platform recommendation

Research date: 2026-08-06

## Recommendation

Build the first vertical slice with **Twilio Programmable Voice as the carrier and call-control layer, Twilio ConversationRelay as the realtime speech relay, and the Voice Agent's LLM, policy, tools, session state, Evidence Record, and Subagent orchestration on `stephens.page`**. The companion PWA should initially provide authentication, task status, policy editing, Evidence Records, and email destinations; it should not place calls in slice 1.

This is the shortest route to the agreed behavior—an inbound call triggers a callback to the registered number, the user asks whether Bountywell is healthy, the server performs a bounded investigation, and the result is spoken and recorded visually—without making a hosted voice platform the owner of operational authority. ConversationRelay sends transcribed prompts to the server and accepts streamed text tokens back, so the server retains the actual dialogue/tool loop while Twilio handles PSTN audio, speech recognition, speech synthesis, endpointing, and interruption. Twilio documents caller interruption events, token streaming, tunable interruption sensitivity, backchannel filtering, and partial/eager prompts; it reports internal ConversationRelay benchmarks of p50 491 ms and p95 713 ms, although production latency must still be measured with the chosen model and network path. [ConversationRelay WebSocket protocol](https://www.twilio.com/docs/voice/conversationrelay/websocket-messages), [ConversationRelay configuration](https://www.twilio.com/docs/voice/twiml/connect/conversationrelay), [Twilio latency claim](https://www.twilio.com/en-us/products/conversational-ai/conversationrelay)

The credible alternative is **LiveKit Cloud for rooms and SIP, a LiveKit Agents worker on `stephens.page`, a Telnyx SIP trunk for PSTN, and a selectable realtime model or STT/LLM/TTS pipeline**. It is the better long-term architecture if browser WebRTC, model/provider experimentation, or control of the full audio pipeline becomes important early. It is not the slice-1 choice because it introduces rooms, SIP trunk configuration, agent-worker lifecycle, and inference integration before the first user-visible outcome. LiveKit's main architectural advantage is that telephone callers and later browser clients are participants in the same room abstraction while the agent remains ordinary Python or Node code under our control. [LiveKit Agents](https://docs.livekit.io/agents/), [LiveKit telephony](https://docs.livekit.io/telephony/), [LiveKit frontends](https://docs.livekit.io/frontends/)

Telnyx Conversation Relay should be kept as the first carrier/relay adapter to benchmark after slice 1. Its published component price is lower than Twilio's and it exposes the same useful high-level shape—hosted STT/TTS connected to our WebSocket—but its current first-party documentation exposes fewer turn-taking controls and no comparable end-to-end latency benchmark. [Telnyx ConversationRelay](https://developers.telnyx.com/docs/voice/programmable-voice/texml-verbs/conversationrelay), [Telnyx Voice API pricing](https://telnyx.com/pricing/voice-api)

## The layers are separate decisions

“Telephone voice agent” combines three replaceable layers:

1. **Carrier/PSTN and call control** owns the phone number, inbound and outbound calls, the Callback Handshake, and optional SIP routing. The serious slice-1 candidates are Twilio and Telnyx.
2. **Realtime voice-agent layer** owns some combination of endpointing, interruption, audio transport, STT, TTS, model access, and tool/event protocol. ConversationRelay, LiveKit Agents, ElevenLabs Agents, OpenAI Realtime, Vapi, and Retell sit here in different ways.
3. **Client transport** is PSTN in slice 1 and later WebRTC in the PWA. WebRTC is the browser/mobile standard that carries live encrypted audio over the internet; it avoids a cellular telephone leg and usually supports wider-band audio, but it depends on a foreground-capable browser, microphone permissions, and a stable data connection.

AT&T and Tello remain the networks on which the registered callback phone is reached. They do not need to be part of the programmable platform selection. 3CX is a PBX and routing/control layer, not a substitute for a realtime speech-and-reasoning layer.

## Slice-1 design

### Call and authentication flow

1. An inbound call to the Twilio number is treated only as a request to begin a Telephone Session. The webhook verifies Twilio's request signature, creates a short-lived callback request, rejects/ends the inbound leg, and never authenticates from caller ID alone.
2. The Voice Agent server calls the one registered number through Twilio's Calls API. The outbound call's TwiML connects to `<ConversationRelay url="wss://…">` with a single-use opaque session identifier—not credentials or sensitive context—in a custom parameter.
3. The ConversationRelay WebSocket validates Twilio's signature and binds the call to the pending callback. Only then does the server create an authenticated Telephone Session.
4. The server receives `prompt` messages, runs the Voice Agent model/tool loop, and streams generated text tokens back immediately. `interrupt` messages cancel the current generation and update the conversation history to what was actually played.

This uses the Callback Handshake as agreed, but it is worth stating its security boundary precisely: it proves current control of the registered telephone endpoint, not possession of the PWA account credential. SIM takeover, call forwarding, and voicemail remain risks. High-risk authenticated policy editing therefore stays in the PWA.

### Server ownership

The WSS application on `stephens.page` should own:

- Voice Agent session state and the Standing Autonomy Policy;
- a provider-neutral stream of user utterances, assistant text chunks, interruption/cancellation, and call lifecycle events;
- bounded tools and the asynchronous job queue that launches Subagents;
- Bountywell health checks and later policy-authorized interventions;
- the redacted transcript and all Evidence Record events;
- callback/email completion preferences and later completion calls.

ConversationRelay should own only the phone/audio session, endpointing, STT, and TTS. A long-running Subagent must never block the WebSocket event loop or model response. The Voice Agent should acknowledge delegation immediately, persist the job, remain conversationally responsive, and either report later in the same call or start a fresh callback after completion.

### Recordkeeping

Do not enable Twilio call recording, `<Record>`, or Conversation Intelligence persistence in slice 1. Store the redacted prompt transcript, text sent for speech, interruption boundaries, tool calls, Subagent milestones, verification, and final result on the Managed Host. This satisfies the agreed Evidence Record without retaining raw audio. Twilio exposes recording only through explicit recording controls, while ConversationRelay can optionally persist transcripts only when an intelligence service is configured. [Twilio recording settings](https://www.twilio.com/docs/voice/recording-settings), [ConversationRelay `intelligenceService`](https://www.twilio.com/docs/voice/twiml/connect/conversationrelay)

### PWA scope

Slice 1 PWA responsibilities remain authentication, callback initiation/status, policy editing, Evidence Record viewing, and completion-email destinations. Add WebRTC as vertical slice 4 using the Twilio Voice JavaScript SDK and route the resulting browser call through the same ConversationRelay TwiML. That preserves one server-side dialogue/tool implementation across PSTN and browser audio. Twilio officially supports its JS SDK in Chrome and Firefox on Android and in current desktop browsers. [Twilio JavaScript Voice SDK](https://www.twilio.com/docs/voice/sdks/javascript)

## Why the alternatives are not slice 1

- **LiveKit** is the likely destination if WebRTC and telephone need to be equal first-class channels. It is deliberately the alternative, not a rejected technology: the first three vertical slices do not need rooms or direct audio control, while ConversationRelay can prove the product interaction sooner.
- **Telnyx Conversation Relay** wins on public price and raw-media capabilities, but the Voice Agent will benefit from Twilio's documented interruption sensitivity, backchannel handling, partial prompts, and latency benchmark during its first conversational-quality work. Put the relay behind an adapter and benchmark Telnyx after the slice succeeds.
- **ElevenLabs Agents** is probably the quickest polished hosted demo and has an excellent direct React/WebRTC path, but it makes the hosted platform the conversation runtime and costs $0.08/min before LLM and telephony. It is a strong company-experiment option when voice character and turnkey tuning matter more than local ownership.
- **OpenAI Realtime** is attractive for direct speech-to-speech and server sideband control. Its official SIP path is inbound-oriented, so a callback-first product needs carrier-side origination/bridging that LiveKit, ElevenLabs, Twilio ConversationRelay, and Telnyx Conversation Relay already make direct.
- **Vapi and Retell** are optimized for rapidly deployed customer-facing agents. Both can use custom LLMs and BYOC, but their proprietary hosted orchestration remains in the middle. That duplicates or obscures the Voice Agent's own job/task/policy model.
- **3CX** should be integrated only when an ETA/company experiment requires existing PBX numbers, extensions, queues, or human transfer. Its Call Control API can serve as a telephony adapter, but building the first speech loop on its 8 kHz raw PCM stream would recreate functionality already supplied by the relays.

## Evolution path

Keep the Voice Agent core independent from Twilio's JSON shapes from the first commit. The telephony adapter should translate provider events into a small internal protocol such as `session_started`, `user_utterance_partial/final`, `assistant_text_chunk`, `assistant_interrupted`, and `session_ended`. Then the vertical path is:

1. Twilio PSTN callback + ConversationRelay + Bountywell read-only health answer.
2. The same channel performs the blind Bountywell Outage Drill under policy and verifies recovery.
3. The same channel delegates the Keeplore Button Trial, opens a PR, and calls or emails when finished.
4. Add PWA WebRTC through Twilio's JS SDK and measure it against PSTN.
5. If WebRTC becomes primary, raw audio/model routing is needed, or relay lock-in becomes costly, implement the same internal protocol on LiveKit Cloud + Agents and move the PWA and SIP callback into LiveKit rooms.
6. For company trials, attach Telnyx/Twilio SIP directly or route through an existing 3CX deployment only where PBX behavior adds value.

Before committing beyond slice 1, run identical scripted conversations over Twilio ConversationRelay and Telnyx Conversation Relay and record: end-of-user-speech to first audible response, interruption-to-audio-stop time, false interruption rate while walking near traffic, transcript error rate on code/service names, callback setup time, disconnect recovery, and total carrier/relay/model cost. Marketing latency figures are not substitutes for this end-to-end test.
